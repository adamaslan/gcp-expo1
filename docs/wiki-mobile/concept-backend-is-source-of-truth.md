# Concept: Backend Is The Source of Truth

When the mobile app and a backend disagree about a shape, the backend wins. Mobile never invents a type that mirrors a Python (or Next.js) schema — it generates one from the backend's OpenAPI, or it hand-types from the actual route file and points back to it. This is rule 1 of the cross-repo workflow in [.claude/CLAUDE.md](../.claude/CLAUDE.md).

## The pattern

Every cross-repo data contract has three artifacts:

1. The authoritative schema (Pydantic / TS interface in the backend)
2. A generated TS type in mobile (`AUTOGENERATED — do not edit` header)
3. A regeneration command checked into mobile (`npm run gen:types`)

When the backend schema changes, three things must happen (rule 8): backend PR merges, web client regenerates, mobile regenerates. A backend PR that doesn't list its frontend follow-ups is incomplete.

## Where it appears

- [[entity-backend-client]] — currently *violates* the pattern. Every response is hand-typed. There is no generated types file.
- [[../MULTI_BACKEND_INTEGRATION.md]] Step 4 — the planned compliance: `openapi-typescript` against gcp3 and holdfold's `/openapi.json`.

## Contradictions / tensions

- ai-text-opt is a Next.js app with no `/openapi.json`. Hand-typing is forced. [[../MULTI_BACKEND_INTEGRATION.md]] Step 4 acknowledges this and asks the hand-typed file to cite the four `route.ts` files it mirrors — a weaker form of the same discipline.
- "Generate, never hand-roll" is easy to state and easy to violate under deadline pressure. The wiki's only enforcement is to flag any new hand-rolled type as a `❓ Open question` and let it surface in lint.

## Why this matters specifically for mobile

The mobile release cycle is slower than the web (App Store / Play Store review). A schema drift caught in web at deploy-time becomes a shipped-bug-in-the-wild on mobile. Type generation is the cheapest way to catch the drift at build time, before the store submission.
