# Decision: No Hand-Rolled Mirror Types

## Decision

The mobile app does not maintain hand-written TypeScript interfaces that mirror Pydantic models from gcp3 or holdemfoldem. Types are generated from each FastAPI's `/openapi.json` via `openapi-typescript`, committed to the repo with an `AUTOGENERATED — do not edit` header, and regenerated by `npm run gen:types`.

## Date

Stated as cross-repo rule 2 in [`.claude/CLAUDE.md`](../.claude/CLAUDE.md). Mobile-specific application planned in [[../MULTI_BACKEND_INTEGRATION.md]] Step 4 (~2026-05-22, not yet executed).

## Context

The mobile app currently hand-types every backend response. Each PR that touches a backend schema risks a silent type drift, and the App Store review cycle means a drift caught on web becomes a shipped mobile bug. The team-wide rule (cross-repo rule 2) already forbids hand-mirrored types; this decision documents the application to mobile.

## Alternatives considered

- **Continue hand-typing.** Rejected — violates the existing rule and has already produced a class of bugs the wiki will track under [[concept-backend-is-source-of-truth#contradictions--tensions]].
- **Use a heavier codegen tool (e.g. `orval`, `openapi-fetch`).** Deferred — `openapi-typescript` produces just the types, no runtime; matches the existing thin-client style of [[entity-backend-client]].
- **Pin types via a published npm package from each backend repo.** Rejected — adds publish/version steps to every backend deploy and couples mobile builds to npm.

## Consequences

**Enables:**
- Schema drift surfaces at `tsc` time, not runtime
- One source of truth per type, owned by the backend
- Easier review: generated diffs are mechanical

**Rules out:**
- Hand-extending generated types in place (extensions must live in adjacent files)
- ai-text-opt full automation — Next.js doesn't expose OpenAPI by default, so its types stay hand-rolled with a citation to the source `route.ts` file (see [[../MULTI_BACKEND_INTEGRATION.md]] Step 4)

**Operational consequences:**
- `gen:types` requires the backends to be reachable. CI doesn't need to regenerate; the committed types are the build input. Regeneration is a local-dev action triggered by the developer when the backend changes.

## Validated by

Not yet — generation isn't wired up. Will be validated when:
- A backend schema change in gcp3 triggers a regen on mobile within the same day (proves the workflow is fast enough)
- A backwards-incompatible change in holdfold breaks `tsc` on mobile before reaching the store (proves the safety net works)
